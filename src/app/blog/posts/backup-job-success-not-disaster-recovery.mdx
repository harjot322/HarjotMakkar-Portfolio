## The Assumption Nobody Checks

When a backup CronJob reports success, it means the backup script ran to completion without crashing. It does not tell you whether the resulting snapshot is complete, internally consistent, or capable of being restored. These are entirely different properties, and conflating them creates a dangerous illusion of recovery readiness.

In production database systems, teams frequently look at green monitoring dashboards, confirm their daily backup jobs report `Status: Succeeded`, and assume their disaster recovery (DR) obligations are met.

Then a catastrophic hardware failure occurs. The team attempts an emergency restore, only to discover:
- The snapshot catalog is missing critical metadata pointers.
- Encryption keys were rotated, rendering historical blob chunks un-decryptable.
- The snapshot was partial: Lucene shard segments were skipped during node write locks.

A backup job that exits with code 0 only proves that the upload process finished. It provides zero proof of recoverability.

## What "Backup Success" Actually Means

A traditional backup job succeeds when:
- The container process starts.
- It triggers a snapshot API call or streams files to object storage.
- It exits with code 0.

Notice what is missing from this equation:
- **Did the storage backend accept and persist all shard chunks without truncation?**
- **Is the snapshot catalog internally consistent?**
- **Can the database engine allocate, reassemble, and query those chunks in a clean environment?**

In our OpenSearch clusters, we found that relying solely on repository snapshot status left critical blind spots. Shard-level snapshot metadata could report `SUCCESS` while leaving indices susceptible to restore-time allocation deadlocks if node discovery configurations differed.

## The Paradigm Shift: The Automated Restore Probe

To bridge the gap between "backup taken" and "system recoverable", backup verification must be engineered as an independent, automated reliability loop.

We designed the **Automated Restore Probe**: an asynchronous verification pipeline that runs on a 15-minute offset after every daily snapshot.

### The 4 Verification Gates Every Restore Probe Must Enforce:

1. **Snapshot Repository Health Assertion**:
   The probe queries the repository API to verify that storage account SAS tokens or IAM roles have not expired, and that snapshot metadata chains are unbroken.
2. **Ephemeral Sandbox Allocation**:
   The probe issues a real restore request for a dedicated canary index (e.g., `probe-verify-2025-05`) into an isolated namespace, proving that Lucene segment files can be downloaded from object storage across the network.
3. **Lucene CRC & Record Sanity Checks**:
   Once the temporary index transitions to `status: green`, the probe queries document counts and verifies that record totals match the pre-backup baseline.
4. **Automated Teardown & Heartbeat**:
   The probe deletes the temporary verification index and emits a cryptographic health heartbeat to Azure Monitor. If the restore hangs or fails for more than 10 minutes, an automated high-priority alert pages the on-call SRE.

## Implications for SRE Practice

Backup verification is an availability concern, not a storage concern. It belongs in core SRE practice because it answers the only question that matters during an outage: **If our production clusters were destroyed right now, could we restore service before our Recovery Time Objective (RTO) expires?**

The correct mental model is not *"do we have backups?"* but *"have we proven we can recover?"*

A system with verified, restorable backups can answer that question with mathematical confidence. A system with unverified backup jobs is simply hoping for the best.

## Practical Takeaways

1. **Decouple verification from backup execution**: Never verify within the same script that took the backup. Run the restore probe as a separate process on a staggered schedule.
2. **Restore actual data, not just metadata**: An API check confirming a snapshot exists is insufficient. You must allocate shards and read records from the restored indices.
3. **Automate cleanup**: A good restore probe leaves zero persistent footprint. It restores, validates, records telemetry, and cleans up after itself.
4. **Treat restore failures as Sev-1 incidents**: If a restore probe fails, you do not have a working backup. Treat it with the same urgency as a production service degradation.

A successful backup job is merely the starting line. Recovery readiness requires continuous, automated proof that your snapshots can actually bring your platform back to life.
