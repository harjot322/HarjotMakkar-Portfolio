## Executive Summary & Problem Statement

In a decentralized enterprise cloud estate spanning more than **400 AWS member accounts**, answering the fundamental question - *"What is actually running across our cloud footprint right now?"* - was a multi-day ordeal.

Before this initiative, inventory gathering relied on ad-hoc Python scripts executed from developer laptops, siloed AWS billing CSV exports, and manually maintained spreadsheets. These manual approaches suffered from critical operational flaws:
- **Zero Centralized Visibility**: Platform leadership, Directors of SRE, and FinOps teams had no single source of truth (SSOT) to audit running services across business units.
- **Runaway Zombie Infrastructure**: Thousands of unattached EBS volumes, abandoned RDS database snapshots, detached Elastic Network Interfaces (ENIs), and idle clusters accumulated silently across development and staging accounts, burning tens of thousands of dollars in monthly cloud spend.
- **Brittle Cross-Account Scripts**: Ad-hoc scripts attempting to iterate through 400+ AWS accounts sequentially were plagued by AWS API rate limiting (`ThrottlingException`), intermittent network timeouts, and partial run failures that corrupted reporting.
- **Credential Sprawl & Security Risks**: Ad-hoc tooling frequently relied on long-lived IAM access keys with broad cross-account permissions stored insecurely across local environments.

To solve this, I designed and deployed an automated, secure, and scheduled ingestion engine. The system queries a centralized **AWS Config Aggregator**, normalizes multi-account configuration items, and loads them into an **Amazon Aurora** analytical store using ephemeral credentials provisioned by **HashiCorp Vault CSI** and **KIAM**. 

The resulting platform feeds an enterprise-grade **Grafana command center** and internal programmatic APIs before regular business hours every morning, eliminating over 90% of recurring reporting effort while tracking more than **200,000 active cloud resources**.

## Architectural Blueprint & System Design

Rather than building a naive distributed crawler that makes thousands of individual API calls against 400+ separate accounts, the system leverages native AWS aggregation paired with a decoupled Kubernetes processing pipeline.

### Core Architectural Components

1. **Centralized AWS Config Aggregator**:
   - Each member account runs an AWS Config recorder collecting configuration snapshots of supported AWS resources.
   - An organization-level AWS Config Aggregator continuously consolidates resource records from all 400+ accounts into a single audit account.
   - This architectural choice eliminated thousands of individual cross-account API calls, avoiding AWS API rate-limiting and removing the need for complex network meshes.

2. **Daily Kubernetes Ingestion Engine (`batch/v1 CronJob`)**:
   - A lightweight Python ingestion container scheduled to execute daily at 04:00 UTC on an existing enterprise EKS cluster.
   - The job runs prior to business hours, guaranteeing that engineering leadership and FinOps teams arrive to freshly computed metrics every morning.
   - Implements high-throughput pagination and robust exponential backoff when querying the AWS Config SQL-like Advanced Query interface.

3. **Decoupled Data Layer (Amazon Aurora)**:
   - Ingested configuration data is parsed, enriched with standardized metadata, and loaded into Amazon Aurora (PostgreSQL-compatible).
   - Storing normalized relational rows alongside `JSONB` configuration blobs decouples analytical reporting from cloud provider APIs. Grafana dashboards and internal services query Aurora directly with sub-second latencies, completely protecting AWS Config API quotas.

4. **Internal APIs & Downstream Consumers**:
   - In addition to human visualization via Grafana, a lightweight internal service exposes REST and GraphQL endpoints for downstream automation, including security compliance audits, CI/CD deployment checks, and FinOps anomaly detectors.

## Defense-in-Depth Security: Zero Static Secrets

A core requirement for this platform was strict adherence to zero-trust credential hygiene. No hardcoded passwords, long-lived AWS secret keys, or static tokens were permitted at any layer of the architecture.

### Ephemeral Authentication & Ingestion Flow
1. **Pod Scheduling**: The Kubernetes CronJob pod starts at 04:00 UTC with an IAM role annotation (`iam.amazonaws.com/role`).
2. **KIAM Pod Identity**: The node-level KIAM DaemonSet intercepts the metadata request and calls AWS STS to assume `ConfigAggregatorReadOnly`.
3. **Short-Lived AWS STS Lease**: AWS STS returns temporary IAM credentials to the CronJob pod bounded by a 1-hour expiration window.
4. **Vault CSI Volume Mount**: The CSI driver contacts HashiCorp Vault to dynamically generate a unique, short-lived PostgreSQL database role and password for Amazon Aurora.
5. **In-Memory Credential Injection**: Vault CSI injects the temporary credentials into an in-memory `tmpfs` volume (`/vault/secrets/db-creds.json`) with zero disk writes.
6. **Aggregated Inventory Extraction**: The CronJob streams inventory across all 400+ accounts via AWS Config `SelectAggregateResourceConfig`.
7. **Relational Upsert**: The pod normalizes the payload and executes bulk upserts into Amazon Aurora.
8. **Automated Teardown**: Upon batch completion, the pod terminates and both the AWS STS session and HashiCorp Vault database leases expire automatically.

### 1. Cross-Account Pod Identity via KIAM
The ingestion CronJob pod runs with a dedicated KIAM role annotation:
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: aws-inventory-aggregator
  namespace: platform-inventory
spec:
  schedule: "0 4 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      template:
        metadata:
          annotations:
            iam.amazonaws.com/role: arn:aws:iam::112233445566:role/ConfigAggregatorReadOnly
        spec:
          restartPolicy: OnFailure
          containers:
            - name: aggregator
              image: internal-registry.enterprise.net/sre/cloud-inventory:v1.4.2
              env:
                - name: AGGREGATOR_NAME
                  value: "EnterpriseMasterConfigAggregator"
                - name: DB_SECRET_PATH
                  value: "/vault/secrets/db-creds.json"
              volumeMounts:
                - name: vault-db-creds
                  mountPath: /vault/secrets
                  readOnly: true
          volumes:
            - name: vault-db-creds
              csi:
                driver: secrets-store.csi.k8s.io
                readOnly: true
                volumeAttributes:
                  secretProviderClass: "aurora-dynamic-db-credentials"
```

The assumed role is strictly scoped via AWS IAM policy conditions, allowing only read-only query operations on the designated Config Aggregator:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowConfigAggregatorRead",
      "Effect": "Allow",
      "Action": [
        "config:SelectAggregateResourceConfig",
        "config:GetAggregateResourceConfig",
        "config:DescribeConfigurationAggregators"
      ],
      "Resource": "*"
    }
  ]
}
```

> [!NOTE]
> **Engineering Context on KIAM**: While KIAM was the enterprise standard in this EKS cluster, modern Kubernetes platforms have largely transitioned to **EKS Pod Identity** or **IAM Roles for Service Accounts (IRSA)** to eliminate the iptables proxy daemonset overhead. The core security principle remains identical: short-lived, STS-assumed role credentials with zero static keys.

### 2. Ephemeral Database Authentication with HashiCorp Vault CSI Driver
Static database credentials represent a primary attack vector in batch jobs. To eliminate this:
- The Kubernetes pod leverages the **HashiCorp Vault CSI Provider** (`secrets-store.csi.k8s.io`).
- When the CronJob pod is scheduled, Vault's database secrets engine dynamically creates a dedicated PostgreSQL user in Aurora with a 1-hour Time-To-Live (TTL).
- The credentials are injected via an in-memory `tmpfs` volume (`/vault/secrets/db-creds.json`) and never written to disk.
- When the job finishes and the pod terminates, the lease naturally expires in Vault, and the temporary database credentials are revoked automatically.

## High-Throughput Ingestion & Query Mechanics

The ingestion engine uses SQL-like syntax against the AWS Config Aggregator using `SelectAggregateResourceConfig`. This allows extracting precise configurations across all 400+ accounts in parallel chunks.

```python
import os
import json
import boto3
from botocore.config import Config

boto_config = Config(
    retries={"max_attempts": 8, "mode": "adaptive"},
    connect_timeout=10,
    read_timeout=30,
)

def fetch_aggregated_inventory(aggregator_name: str, query: str):
    """
    Executes a paginated Advanced Query against the AWS Config Aggregator.
    Returns a stream of normalized resource configuration dictionaries.
    """
    client = boto3.client("config", config=boto_config)
    next_token = None
    
    while True:
        kwargs = {
            "ConfigurationAggregatorName": aggregator_name,
            "Expression": query,
            "Limit": 100,
        }
        if next_token:
            kwargs["NextToken"] = next_token

        response = client.select_aggregate_resource_config(**kwargs)
        raw_results = response.get("Results", [])

        for item in raw_results:
            parsed = json.loads(item)
            yield {
                "account_id": parsed.get("accountId"),
                "region": parsed.get("awsRegion"),
                "resource_type": parsed.get("resourceType"),
                "resource_id": parsed.get("resourceId"),
                "resource_name": parsed.get("resourceName"),
                "configuration": parsed.get("configuration"),
                "tags": parsed.get("tags", []),
            }

        next_token = response.get("NextToken")
        if not next_token:
            break
```

### Idempotent Batch Persistence & Schema Design
To guarantee that retrying a failed CronJob run never produces duplicate entries or corrupts historical trendlines, database persistence relies on partitioned upsert semantics:

```sql
CREATE TABLE IF NOT EXISTS cloud_resource_snapshots (
    snapshot_date    DATE NOT NULL,
    account_id       VARCHAR(20) NOT NULL,
    aws_region       VARCHAR(30) NOT NULL,
    resource_type    VARCHAR(100) NOT NULL,
    resource_id      VARCHAR(255) NOT NULL,
    resource_name    VARCHAR(255),
    tags             JSONB,
    configuration    JSONB,
    created_at       TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (snapshot_date, account_id, resource_type, resource_id)
) PARTITION BY RANGE (snapshot_date);

-- Daily partition creation and automated cleanup
CREATE INDEX idx_resource_lookup ON cloud_resource_snapshots (resource_type, account_id);
CREATE INDEX idx_resource_tags ON cloud_resource_snapshots USING GIN (tags);
```

### Managing Database Storage & Pruning
Tracking 200,000+ resources daily generates approximately 6 million records per month. To maintain sub-second Grafana query latencies:
- **Table Partitioning**: Partitions are created dynamically per month.
- **Automated Retention Lifecycle**: A secondary lightweight maintenance job purges full `configuration` JSON payloads older than 90 days while preserving daily roll-up counts (`account_id`, `resource_type`, `count`) in a permanent summary table for multi-year trend analysis.

## FinOps Impact: Hunting Down "Zombie Resources"

While the dashboard gave engineering leadership instant situational awareness, its most immediate return on investment came from **FinOps cloud waste reclamation**.

In a 400-account environment without automated enforcement, orphaned resources accumulate unnoticed:

- **Unattached EBS Volumes (`13,444 Total`)**: **1,200+ unattached volumes** in `available` state following uncoordinated EC2 terminations (~$18,000 to $24,000 in monthly waste).
- **Orphaned DB Snapshots (`19,000+ Total`)**: **6,500+ orphaned manual snapshots** older than 90 days lingering in staging accounts (~$12,000 to $15,000 in monthly waste).
- **Idle Elastic IPs & Dangling ENIs (`32,900+ Total`)**: **800+ unattached Elastic IPs and orphaned ENIs** driving IPv4 hourly charges and CIDR exhaustion.

1. **Unattached EBS Volumes**:
   - The query filtered volumes where `attachment.status` was null or `available`. Over 1,200 unattached EBS volumes (many provisioned as expensive `gp3` or `io1` with pre-allocated IOPS) were sitting idle following improper EC2 terminations.
   - Surfacing this list enabled automated cleanup tickets, saving an estimated **$20,000+ per month** in unneeded storage.
2. **Orphaned DB Snapshots**:
   - Over 6,500 manual RDS snapshots had been created prior to major software releases in staging environments and never deleted, accumulating petabytes of cold backup storage.
3. **Stale IAM Roles & Cloud Surface Area**:
   - Auditing over 97,600 IAM roles exposed hundreds of dormant roles left behind by decommissioned services, enabling security teams to systematically shrink the organization-wide attack surface.

## Architectural Realities: Engineering Trade-Offs & Honest Nuances

A production case study is only credible when it honestly discusses architectural trade-offs, discrepancies between marketing language and implementation reality, and technical limitations.

### 1. "Almost Real-Time" vs. Daily Snapshot Semantics
- **The Marketing Pitch**: Marketing descriptions often label operational dashboards as "real-time" command centers providing "live resource counts."
- **The Engineering Reality**: In an estate of 400+ accounts and 200,000+ resources, continuous real-time streaming is both cost-prohibitive and unnecessary for strategic infrastructure governance.
- **The Deliberate Trade-Off**: Running a daily batch snapshot at 04:00 UTC prior to business hours provided an exact, stable, and immutable baseline for day-over-day delta comparisons. As the production Grafana dashboard header explicitly clarifies:
  > *"Data is loaded daily as a snapshot prior to regular business hours and does not reflect the count as of right now."*
- Attempting an event-driven, real-time EventBridge forwarding architecture across 400 accounts would have increased infrastructure complexity by orders of magnitude while providing negligible value for FinOps forecasting and capacity planning.

### 2. KIAM Legacy Footprint vs. Modern EKS Pod Identity
- The system utilized **KIAM** to intercept AWS metadata API calls from the CronJob container. While KIAM was the robust standard at the time of initial rollout, running a daemonset that modifies node iptables carries operational fragility during node OS upgrades and EKS minor version bumps.
- Modern iterations of this pipeline should migrate directly to **EKS Pod Identity** or **IRSA**, leveraging native AWS OIDC web identity tokens to eliminate daemonset dependencies completely.

### 3. Diagram Data Flow vs. Execution Semantics
- In architectural schematics, the arrow connecting AWS Config to the Kubernetes CronJob visually represents configuration data flowing into the worker. In execution reality, the CronJob initiates outbound HTTPS pull requests to the AWS Config endpoint using authenticated STS credentials, pulling paginated result pages over port 443.

## Key Takeaways & SRE Principles

1. **Leverage Cloud-Native Aggregation Before Writing Custom Crawlers**: Building custom concurrent boto3 scripts to poll hundreds of accounts is an anti-pattern. Native cloud primitives like AWS Config Aggregators handle cross-account data collection, rate-limiting, and error isolation far more reliably than bespoke application code.
2. **Decouple Analytics from Provider APIs**: Never hook operational visualization dashboards directly to cloud provider management APIs. Ingesting data into an analytical database like Amazon Aurora protects API rate quotas, enables multi-table joins, and delivers instantaneous sub-second user queries.
3. **Enforce Ephemeral Credentials Across Every Hop**: A system is only as secure as its weakest integration. Combining Kubernetes pod identity for AWS authorization with HashiCorp Vault dynamic secret generation for database authentication guarantees that even a compromised container leaves behind zero persistent credentials.
4. **Visibility Precedes Optimization**: You cannot optimize, secure, or govern what you cannot see. Establishing a single source of truth across 400+ accounts transformed FinOps and platform engineering from a reactive game of guessing into an empirical, data-driven discipline.
