This document is deliberately written to avoid naming clients, end-clients, third-party contractors, customer organizations, regulated organizations, or confidential business partners.

**Do not add those names back into the public website.** Apply the same rule to:
- Website pages and page metadata.
- Résumé and downloadable PDF.
- Project case studies and architecture diagrams.
- Screenshots, terminal output, dashboards, logs, and alt text.
- GitHub repositories, READMEs, commit examples, and demo data.
- LinkedIn, Substack, social posts, conference bios, and testimonials.
- OpenGraph descriptions, SEO metadata, structured data, and image filenames.

Do not reveal internal project codenames, acronyms, environment labels, hostnames, repository names, account identifiers, tenant IDs, subscription IDs, IP addresses, internal URLs, secrets, or proprietary architecture.

Names of former employers, agencies, contractors, customers, and partners are intentionally omitted from the career narrative. Use neutral descriptions such as:
- “Remote Cloud SRE engagement”
- “A US-based enterprise environment”
- “A regulated enterprise environment”
- “A large multi-account cloud estate”
- “An internal deployment utility”
- “A multi-tenant cloud project environment”

Even neutral descriptions can reveal an organization when combined with unusual details. Generalize further when necessary.

## Metrics are not automatically public

All metrics in this document are candidate claims collected from previous career discussions and supplied résumé material. Before publishing, verify:
1. The number is accurate.
2. The measurement period and denominator are understood.
3. Your personal contribution is represented accurately.
4. The figure is not confidential or commercially sensitive.
5. The contract and applicable NDA permit disclosure.

If approval is uncertain, use qualitative wording or a less specific scale. Do not assume that removing an organization’s name makes a project detail safe to disclose.

# 10. Engineering philosophy and working principles

These principles can form an “How I Work” section on the website.

## Infrastructure as software

Infrastructure should be version-controlled, reviewable, declarative, repeatable, and testable. Large infrastructure changes should remain auditable and understandable.

## Reliability beyond “it ran”

A successful process exit code is not proof of system health. Backups need verification. Migrations need traffic validation. CI/CD needs meaningful reliability indicators. Production systems need recovery paths.

## Automation tied to measurable impact

Automation should reduce repetitive effort, improve consistency, reduce error rates, and free engineering time. Automation is not valuable merely because it uses a script.

## Security embedded in delivery

Security and quality checks should be integrated into normal engineering workflows. Access should be controlled, secrets should be handled carefully, and findings should have clear remediation paths.

## Operational ownership

A production system must be observable, debuggable, supportable, and recoverable after deployment. Dashboards, alerts, runbooks, backups, and rollback plans are part of the engineering deliverable.

## Root-cause troubleshooting

Use evidence. Inspect telemetry and logs, isolate the failure domain, test assumptions, and validate the fix. Avoid speculative changes that make the system harder to understand.

## FinOps and pragmatic simplicity

Infrastructure decisions have ongoing costs. Identify idle resources, understand capacity, automate safe cleanup, and prefer maintainable solutions over unnecessary complexity.

## Clear technical communication

Good engineering includes documenting decisions, explaining trade-offs, and making systems understandable to the next person who has to operate them.
